# 目的と段階的な進め方

## 合意済みの要件

- 対象は NVIDIA Jetson Orin Nano（Tegra234）。
- NVIDIAが提供する開発環境でコンパイルしたコードを動かす。
- NVIDIA提供のOP-TEEおよびfTPM TAを対象とする。
- NVIDIA提供ソースのQEMU対応変更を極力抑える。
- CUDAによるGPUコードの実行は必須としない。
- fTPMの利用者から見た機能を実機と同等にする。詳細な比較項目は別途確定する。
- ソースコード、ビルド手順、調査結果は本リポジトリで管理する。
- 作業はステップごとに結果を確認しながら進める。

## 現在地

対象のJetPack／Jetson Linux（L4T）は未選定。ビルド・実行環境も未整備。
QEMU上でのNVIDIA版OP-TEE／fTPMの実行はまだ検証していない。

## ステップ1：対象リリースの選定（次に行う作業）

公式資料から次を確認して候補を提示し、採用するリリースを決める。

1. Jetson Orin Nanoへの対応。
2. OP-TEEとfTPM TAのソース、ビルド手順、対応ツールチェーンの入手性。
3. ソースのタグ／コミットと配布物の対応、ライセンス条件。

この段階では「最新版」を推測で採用せず、公式URLと確認したバージョンを記録する。

## 以降の作業順序

1. 採用リリースのソースとツールチェーンを取得し、版を固定する。
2. OP-TEEの起動とfTPMに必要なTegra固有機能をソースから調査する。
3. NVIDIAソースの変更量とQEMU実装量を比較し、最小の実装範囲を決める。
4. 起動、TAロード、TPMコマンド、永続化の順に動作を確認する。

## eFuseについて調査すること

- 識別子や設定値のレジスタ読み出し経路。
- 秘密値に依存する鍵導出、暗号エンジン、鍵スロットとの関係。
- 他のファームウェアを経由するサービスの有無。
- セキュアストレージ、TPMの永続状態、EK／証明書との関係。

eFuseレジスタだけの実装で十分とは、まだ判断しない。
仮想デバイスごとのテスト用秘密と識別子を永続化する設計を検討する。
実機の秘密の複製は前提としない。
再起動、TPMクリア、OS再インストール、仮想マシンの複製・スナップショットで
何が保持されるかを明文化する。

## 未確定事項

- Jetson用バイナリ自体の無変更実行が必要か、同じソースの再ビルドでよいか。
- ブートチェーン全体の再現が必要か、OP-TEE／fTPMを起動できればよいか。
- TPM機能同等性の範囲：PCR、NV、鍵、seal／unseal、EK証明書、認証など。
- ホストOSとCPU、利用できる計算資源、実機での比較試験の可否。

## 注意点

標準QEMUのAArch64 virtマシンはTegra234を再現しない。
NVIDIAツールチェーンでコンパイルできることと、実機用バイナリが動くことは別に検証する。
仮想eFuseで機能を再現しても、実機のハードウェア保護を再現したことにはならない。
