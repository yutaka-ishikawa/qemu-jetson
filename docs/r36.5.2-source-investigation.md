## ビルド構成

`optee/atf_and_optee_README.txt` と `optee_src_build.sh` を確認。

- 公式コマンドは `./optee_src_build.sh -p t234 -t`。`-t` がfTPMを有効化する。
- `CROSS_COMPILE_AARCH64_PATH`、AArch64 GCC、pkg-configが必要。
- `UEFI_STMM_PATH` に既存のStMMイメージが必要。ソースパッケージだけでは公式ビルドの入力が揃わない。
- `PLATFORM=tegra`、`PLATFORM_FLAVOR=t234` を指定する。
- 最初にOP-TEEとTA開発キットをビルドし、client、samples、fTPMを構築する。
- fTPMに `CFG_TA_MEASURED_BOOT=y` と `CFG_USE_PLATFORM_EPS=y` を指定する。
- fTPM TAとftpm-helper TAをEarly TAとして埋め込み、StMMを含めてOP-TEEを再ビルドする。
- T234では `optee/optee_os/prebuilt/t234/libcommon_crypto.a` をリンクする。
- ATFは別の `atf_src.tbz2`。最終TOSイメージ生成にはBSP内の `gen_tos_part_img.py` も必要。

OP-TEEの `mk/config.mk` の既定バージョンは4.2。
fTPMソースは `optee/samples/ms-tpm-20-ref/Samples/ARM32-FirmwareTPM/optee_ta/`。
この配布物の `TPMCmd/tpm/include/TpmTypes.h:295` には `SPEC_VERSION 162` とある。
R36.4.4についての公式比較文書のRevision 1.59を、この配布物に転用してはならない。
正確な上流コミットは今回未特定のため、配布アーカイブのハッシュを基準とする。

## ハードウェア依存と境界

| 機能 | 根拠となるソース | 確認内容 |
| --- | --- | --- |
| Tegraプラットフォーム | `optee/optee_os/core/arch/arm/plat-tegra/conf.mk` | Fuse、SE、SE RNG1、Jetson user key PTA、TCUを有効化。T234は12コア設定、Pointer Authenticationも有効 |
| Fuse読み取り | `optee/optee_os/core/drivers/tegra/t234/tegra_fuse.c` | MMIOレジスタからBSIとsecurity modeを取得し、ECIDとSNを初期化 |
| デバイス識別子 | `optee/optee_os/core/drivers/tegra/common/tegra_driver_fuse.c` | vendor／fab／lot／wafer／座標などからECID、ODMID0/1とODM_INFOからSNを生成 |
| シード受け渡し | `optee/optee_os/core/pta/tegra/jetson_ftpm_helper_pta.c` | DTから `nvidia,ftpm-seed`、firmware ID秘密鍵と証明書を取得 |
| EPS導出 | 同上 `get_prop_endorsement_seed()` | HKDF-SHA256を使用。Fuse SNとEKBのSNを照合し、EKBのEPS_Seedも使用 |
| EKBとストレージ鍵 | `optee/optee_os/core/pta/tegra/jetson_user_key_pta.c` | OEM_K1／OEM_K2のSE鍵スロットを利用する経路あり |
| TPM NV保存 | fTPMの `platform/NVMem.c` | OP-TEEの `TEE_STORAGE_PRIVATE` による永続オブジェクト |

Tegraの公式設定ではRPMB FSを無効化している。最初の機能試験はREE FSによる
永続化を検討できるが、ストレージ暗号鍵も同じ仮想デバイスの状態として管理する必要がある。

## 未Fuse向けの既存経路

`optee/samples/ftpm-helper/host/tool/README_keylime_TPM_for_unfused_Jetson.md`
には、未Fuse実機で `ftpm_sim_provisioning_tool.sh` を使う手順がある。
これはQEMUマシンモデルの提供やTegra依存性の解消を意味しない。

fTPMの `platform/EPS.c` は、OP-TEEの `com.microsoft.ta.endorsementSeed`
プロパティが取得できなければ乱数でEPSを作る。
Helper PTAもDT／EKBがない場合はprovisioning非対応として初期化自体は成功を返す。
このため、最初のTPM機能試験と、Fuse由来のデバイス同一性の再現を段階的に検証できる可能性がある。
ただしOP-TEE全体がQEMUで起動することや、永続化の正しさは未検証。

同PTAには `CFG_JETSON_FTPM_HELPER_INJECT_EPS` の条件付きコードも存在するが、
公式ビルドスクリプトでは有効化していない。初期化・呼び出し経路を未検証のため採用しない。

## ライセンスの確認結果

- OP-TEE OSの基本ライセンスとFuseドライバ、ftpm-helperなどにはBSD系の表記がある。
- ms-tpm-20-refのLICENSEはMicrosoftのBSDライセンス。ただし個別ファイルの条件も確認が必要。
- `optee/optee_os/LICENSE.NVIDIA` はCCCヘッダ2点と `libcommon_crypto.a` を別条件の対象として列挙。
- 未Fuse向けKeylime READMEには `LicenseRef-NvidiaProprietary` の表記がある。

パッケージ全体を一律にBSD扱いしない。本コミットには調査文書のみを追加し、
NVIDIAのアーカイブ、バイナリ、個別文書の全文は公開リポジトリへ転載していない。
今後は公式取得元とハッシュで原本を管理し、取り込むファイルごとに条件を確認する。

## 実装方針への含意

NVIDIAソースを無変更のまま動かすには、Fuse以外にSE／RNG、コンソール、
起動時のメモリ・DTとATFとの受け渡しなども調査・再現対象となる。
現時点で「virtにFuseだけ追加すれば動く」とは言えない。

次のステップはツールチェーンとBSPのStMMを揃え、**無変更のT234向けビルドを成立させる**こと。
その成果物と依存一覧を基準に、QEMU側で再現する範囲と、最小限の
プラットフォーム対応が必要な範囲を決める。GPUの実装は不要。
